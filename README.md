Briefly summarize The Gaming Room client and their software requirements. Who was the client? What type of software did they want you to design?
The client for this course was The Gaming Room, a company that wanted to expand their game Draw It or Lose It from an Android-only application to a cross-platform solution. The client required a scalable, distributed software design that could support multiple users, teams, and game sessions simultaneously across different operating systems. The primary goal was to design a system that allowed efficient memory usage, centralized storage of image assets, secure networking, and consistent performance across platforms.
What did you do particularly well in developing this documentation?
One area that went particularly well was analyzing system architecture and making platform recommendations. Creating the software design document helped clarify how operating systems, memory management, storage, and networking all interact within a real-world application. I was able to clearly explain technical concepts in a way that would be understandable to both developers and non-technical stakeholders, which is an important skill in professional software development.
What about the process of working through a design document did you find helpful when developing the code?
Working through the design document before focusing on implementation was very helpful. The process of documenting requirements, constraints, and architectural decisions provided a strong foundation for understanding how the application should function before any code was written. This approach reduced ambiguity, helped identify potential issues early, and reinforced the importance of planning before development.
If you could choose one part of your work on these documents to revise, what would you pick? How would you improve it?
If I could revise one part of my work, I would improve the level of detail in the distributed systems section. While the overall architecture was sound, adding diagrams or more detailed explanations of data flow between clients and servers would make the document even clearer. Improving this section would strengthen communication with future developers who might work on the project.
How did you interpret the user’s needs and implement them into your software design? Why is it so important to consider the user’s needs when designing?
Interpreting user needs was central to the design of Draw It or Lose It. The client needed fast image rendering, support for multiple concurrent games, and cross-platform compatibility. By focusing on these needs, I was able to recommend solutions such as cloud storage, efficient memory usage, and a Linux-based server environment. Considering user needs is critical because software that does not align with client expectations or user experience goals is unlikely to succeed, regardless of how well it is coded.
How did you approach designing software? What techniques or strategies would you use in the future to analyze and design a similar software application?
In the future, I will continue to approach software design by starting with clear requirements analysis and system architecture planning. Techniques such as modular design, scalability planning, and early consideration of security and performance will guide my process. I would also use iterative reviews and documentation updates to ensure the design remains aligned with evolving requirements when designing similar software applications.

# CS 305 Module Eight Journal – Artemis Financial

## Project Overview and Reflection

For this project, I worked as a software developer for Global Rain, a software engineering company that provides services to Artemis Financial. Artemis Financial is a consulting company that develops personalized financial plans for customers, including savings, retirement, investments, and insurance. The company wanted to improve the security of its software application to protect sensitive customer information. My responsibility was to identify potential security vulnerabilities and implement improvements such as secure HTTPS communications, cryptographic hashing, and certificate management.

One aspect of this project that I did well was implementing security improvements to the application and learning how to identify potential vulnerabilities. I configured the application to use HTTPS and worked with SHA-256 hashing to support data integrity. Coding securely is important because it helps protect confidential information from unauthorized access, manipulation, and security breaches. For a financial organization such as Artemis Financial, strong software security also helps maintain customer trust, protect the company's reputation, and reduce the possibility of financial losses.

One of the most challenging parts of the vulnerability assessment process was working with the OWASP Dependency-Check tool. I encountered problems updating the vulnerability database because of an API key configuration issue. Although the scan generated a report identifying potentially vulnerable dependencies in an earlier course project, the database update error prevented me from treating those findings as a complete assessment of the refactored Project Two application. This experience helped me understand how security tools work and why developers must carefully review their results instead of assuming that every scan is successful.

I increased the layers of security in the application by implementing HTTPS, configuring a self-signed SSL certificate, and incorporating SHA-256 checksum functionality. HTTPS helps encrypt information transmitted between the client and server, while SHA-256 hashing helps detect changes to data. In the future, I would use vulnerability assessment tools such as OWASP Dependency-Check, review software dependencies for known security issues, and follow established secure coding guidelines. I would also evaluate the application's security requirements before deciding which mitigation techniques are most appropriate.

To check that the application remained functional after making security improvements, I ran the refactored Java application in Eclipse. The console confirmed that the Spring Boot application started successfully and that the embedded Tomcat server was running on port 8443 using HTTPS. I also used dependency-check reports to examine potential security risks in third-party libraries. Additional testing would be necessary to confirm that the refactored application has no newly introduced vulnerabilities. This project taught me that successful application startup is only one part of validating software security.

Several resources and tools were useful throughout this project, including Eclipse IDE, Java, Spring Boot, Java Keytool, Maven, and OWASP Dependency-Check. I also used cryptographic techniques such as SHA-256 hashing and SSL/TLS certificate configuration. These tools and practices will be useful in future software development projects because they provide ways to identify vulnerabilities, protect information, and verify application functionality. I also learned the importance of troubleshooting configuration errors and documenting security testing results.

One example of work I could show future employers is my Artemis Financial Practices for Secure Software Report and the accompanying refactored Java application. These artifacts demonstrate my experience with Java development, HTTPS configuration, cryptographic hashing, certificate management, and security testing. They also demonstrate my ability to troubleshoot technical problems and document software security improvements. Overall, this project helped strengthen my understanding of secure software development and gave me practical experience that I can apply in my future career as a software engineer.
